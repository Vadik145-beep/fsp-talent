# Защита от фиктивных вакансий и интеграция с ATS

ТЗ, раздел 2: «будет плюсом: механизм защиты от фиктивных вакансий и недобросовестных
работодателей, интеграция с внутренними ATS-системами работодателей». Критерий 6.6 —
дополнительный функционал. Ниже — как это устроено у нас: что уже работает в коде и что
планируем сделать вместе с ФСП после хакатона.

## 1. От чего защищаемся

- **Фиктивная вакансия.** Под видом работы просят деньги за «обучение», собирают
  персональные данные, заманивают в сетевой маркетинг.
- **Недобросовестный работодатель.** Рассылает приглашения всем подряд, указывает одну
  зарплату, а предлагает другую, грубит, пропадает после созвона.
- **Захват данных кандидатов.** Компания-однодневка регистрируется, чтобы выгрузить
  контакты.

Первая защита уже заложена в механике подбора: до принятия приглашения рекрутер видит
обезличенный профиль, без ФИО и контактов. Контакты раскрываются только после согласия
кандидата. У рекрутера квота активных приглашений (по умолчанию 20), поэтому массовая
рассылка невозможна. Вилка зарплаты в приглашении обязательна, и она не может быть ниже
минимальной зарплаты кандидата.

## 2. Скоринг надёжности работодателя

Скоринг — число от 0 до 100. Он виден администратору в разделе «Компании» вместе с
составляющими. Формула простая и прозрачная: админ должен понимать, откуда взялось число.

### Что считается сейчас (реализовано)

Код: `backend/app/companies/service.py`, функция `trust_score`.

| Сигнал | Вклад |
|---|---|
| Доля приглашений, на которые кандидат ответил (принял или отклонил), среди тех, где ответ уже мог быть | база `30 + 50 × доля`; данных нет — 50 |
| Почта рекрутеров на домене компании (`verified_domain`) | +10 |
| Подтверждённая жалоба кандидата | −15 за каждую |
| Жалоба в работе (новая или на рассмотрении) | −5 за каждую |
| Отклонённая жалоба | 0 |

Пример: у компании 10 завершённых приглашений, ответили на 6, домен подтверждён, одна
жалоба подтверждена: `30 + 50 × 0,6 + 10 − 15 = 55`.

### Что добавим (план)

| Сигнал | Как проверять | Почему важно |
|---|---|---|
| Домен почты | Письмо со ссылкой на адрес вида `hr@домен-компании`; домен совпадает с сайтом из профиля; у домена есть MX-запись. Бесплатные почтовые сервисы не подтверждают компанию | Однодневке трудно получить корпоративный домен со своим сайтом |
| ИНН | Сверка с открытыми данными ФНС (выписка ЕГРЮЛ/ЕГРИП, сервис «Прозрачный бизнес») напрямую или через агрегатор с API. Смотрим: организация действует, дату регистрации, вид деятельности (ОКВЭД 62.xx, 63.xx — IT), признаки недостоверности сведений | Ликвидированная или созданная неделю назад фирма без IT-деятельности — повод проверить вручную |
| Реакция на отклики | Доля откликов, которые рекрутер открыл и по которым сменил статус | Компания, которая не читает отклики, тратит время кандидатов |
| Причины отказов | Доля отказов с причиной «зарплата не та», «не та вакансия» | Систематическое расхождение условий — признак обмана |
| Отзывы приглашений | Доля отозванных рекрутером приглашений | Спам-рассылка с последующим отзывом |
| Возраст на платформе | Дни с регистрации, число нанятых без жалоб | Новичкам доверяем меньше, пока нет истории |

Каждый сигнал — отдельная строка в разбивке скоринга. Веса подбираем по накопленным
данным: сколько компаний с низким скорингом потом получили подтверждённые жалобы.

## 3. Ограничения для новых компаний (план)

Новая компания работает в «пробном режиме», пока не выполнено одно из условий: домен
подтверждён и ИНН сверен, либо прошло 14 дней без жалоб.

- квота активных приглашений — 5 вместо 20;
- вакансии проходят модерацию до публикации;
- регулярные задания раздаются не больше чем 20 кандидатам;
- выгрузка через API-токен и вебхуки — только после выхода из пробного режима.

Автоматические меры по скорингу:
- скоринг ниже 30 — вакансии компании уходят на модерацию, админ получает уведомление;
- три подтверждённые жалобы — предложение заблокировать компанию.

## 4. Жалобы и блокировка (реализовано)

Код: `backend/app/admin/service.py` (`ReportService`), `backend/app/companies/antifraud.py`.

1. Кандидат жалуется на компанию: `POST /api/reports` с причиной (фиктивная вакансия, спам,
   зарплата не та, грубость, другое) и текстом. Пожаловаться можно только на компанию, с
   которой был контакт: приглашение, отклик или задание. Это защищает от накрутки жалоб
   конкурентами. Пока жалоба на рассмотрении, вторую на ту же компанию подать нельзя.
2. Админ видит очередь `GET /api/admin/reports`: новые сверху.
3. Админ берёт жалобу в работу (`in_review`), затем подтверждает (`resolved`) или
   отклоняет (`rejected`). При подтверждении можно сразу заблокировать компанию
   (`block_company: true`).
4. Подтверждённая жалоба снижает скоринг компании на 15, жалоба в работе — на 5.
5. Каждое действие пишется в журнал (`audit_log`): жалоба подана, взята в работу,
   решена, компания заблокирована.

Что делает блокировка (проверка `ensure_company_active` → 403 `company_blocked`):
- рекрутеры компании не могут отправлять приглашения, создавать и публиковать вакансии,
  создавать задания и раздавать их повторно, выгружать данные по API-токену;
- опубликованные вакансии компании скрыты из ленты соискателя, задания компании
  не раздаются кандидатам (фильтр `active_company_ids()`);
- уже отправленные приглашения и полученные отклики не удаляются — история остаётся
  для разбора.

## 5. Интеграция с ATS

### Что реализовано

Код: `backend/app/integrations/`.

**API-токен компании.** Администратор компании выпускает токен
(`POST /api/companies/my/api-tokens`) и отзывает его. Токен показывается один раз, в базе
хранится только его хеш SHA-256. Выпуск и отзыв пишутся в журнал.

**Выгрузка.** `GET /api/companies/ats/export` с заголовком `X-Api-Token`. Отдаёт вакансии,
приглашения и отклики компании. Контакты кандидата — только у принятых приглашений и у
откликов (кандидат сам дал согласие). Параметр `since` отдаёт только изменения после
указанного момента — ATS может забирать данные раз в час.

**Вебхуки.** Администратор компании добавляет адрес и выбирает события:

| Событие | Когда | Что внутри |
|---|---|---|
| `invitation.accepted` | Кандидат принял приглашение | приглашение, вилка, категория, кандидат с контактами |
| `application.created` | Кандидат откликнулся на вакансию | вакансия, сопроводительное письмо, кандидат с контактами |
| `ping` | Кнопка «Проверить» | тестовое сообщение |

Каждый запрос подписан. Заголовки: `X-FSP-Event`, `X-FSP-Delivery` (id доставки — для
защиты от дублей), `X-FSP-Timestamp` и
`X-FSP-Signature: sha256=<HMAC-SHA256(секрет, timestamp + "." + тело)>`. Получатель
пересчитывает подпись своим секретом и отбрасывает старые запросы по времени.

Доставка надёжная: событие сначала записывается в таблицу доставок, потом отправляется. Если
адрес не ответил 2xx, делаем повтор через 1 мин, 5 мин, 30 мин, 2 ч — всего 5 попыток, потом
статус `failed`. Журнал доставок виден компании. Повторы отправляет
`python -m app.integrations` (cron раз в минуту).

На проде адреса внутренней сети и localhost запрещены
(`INTEGRATIONS_ALLOW_PRIVATE_URLS=false`) — защита от SSRF.

### Как это ложится на популярные ATS

Общий подход одинаков для любой ATS. Сущности платформы переводятся в сущности ATS:

| fsp-talent | Типичная сущность ATS |
|---|---|
| Вакансия | Вакансия (job) |
| Кандидат после принятия приглашения или отклика | Кандидат / соискатель (candidate, applicant) |
| Принятое приглашение, отклик | Кандидат на вакансии на первом этапе воронки, источник «ФСП» |
| Категория, грейд, результаты теста по темам, бейджи ФСП | Метки и дополнительные поля |
| Причина отказа кандидата | Причина отказа |
| Оценка регулярного задания 0–3 | Комментарий или оценка интервьюера |

Два способа подключения:
1. **Мы шлём события.** Небольшой адаптер (у нас или у работодателя) принимает вебхук,
   проверяет подпись и вызывает API ATS «создать кандидата и добавить на вакансию».
2. **ATS забирает данные сама.** Раз в N минут адаптер вызывает нашу выгрузку с `since`
   и создаёт или обновляет записи.

По конкретным системам — только то, что известно из открытых материалов. Точные методы и
поля сверяем с документацией при подключении конкретного работодателя.

- **Хантфлоу.** Есть публичный REST API и вебхуки. Кандидат из нашего события создаётся как
  соискатель, затем добавляется на вакансию с источником «ФСП». Обратные вебхуки Хантфлоу
  (смена этапа) можно принимать, чтобы показывать кандидату статус.
- **Potok.** По открытым материалам есть API для интеграций, документация выдаётся
  клиентам. Подход тот же: адаптер на вебхуках или периодическая выгрузка.
- **Greenhouse.** Публично описаны Harvest API (кандидаты, заявки, вакансии) и
  Ingestion API для партнёров — источников кандидатов. Наш сценарий — роль партнёра-источника:
  кандидат приходит в Greenhouse с пометкой источника.

Персональные данные (152-ФЗ): до согласия кандидата в ATS уходит только обезличенная
информация. Контакты передаются после принятия приглашения или отклика.

### Что добавим (план)

- События `invitation.declined`, `application.status_changed`, `task.graded`.
- Вместо постоянного токена — OAuth 2.0 (client credentials) с ограниченным сроком и
  правами на чтение.
- Ограничение частоты запросов к выгрузке, список разрешённых IP, смена секрета вебхука
  без простоя (два секрета на переходный период).
- Готовые адаптеры для двух-трёх ATS, которыми пользуются партнёры ФСП.
