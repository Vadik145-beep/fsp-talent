# Механика тестирования кандидатов

Документ описывает, как платформа определяет грейд кандидата, почему тест устойчив
к распространению заданий и чем это подтверждено. Код: `backend/app/testing/engine/`
(чистая библиотека на Python + numpy, без БД и веба), тесты: `backend/tests/engine/`.

## Коротко

1. **Задача — это шаблон, а не текст.** Шаблон генерирует вариант по случайному числу
   (seed): свои числа, имена, данные, код и порядок ответов. У каждого кандидата свой
   вариант, проверка ответа автоматическая. Каждый шаблон даёт от 50 разных вариантов.
2. **Сложность измерена, а не угадана.** У шаблона есть два параметра модели IRT:
   сложность `b` и различающая сила `a`. Сначала их задаёт эксперт, потом они
   пересчитываются по реальным ответам.
3. **Тест адаптивный.** Следующая задача подбирается под текущую оценку уровня кандидата.
   Тест короткий (6–15 задач), а точность как у длинного фиксированного.
4. **Грейд — по шкале уровня θ.** Пороги θ для Стажёр / Junior / Middle / Senior.
   Принудительно грейд не понижается. Смена грейда — не чаще раза в 90 дней.
5. **Утечки ловятся автоматически.** Если задачу начали решать «слишком хорошо и слишком
   быстро», детектор выводит её из оборота.

## 1. Шаблоны задач

Шаблон хранит: специализацию, тему, целевой грейд, формат, генератор, проверку,
параметры `a`, `b`, статус (`draft` черновик → `pilot` непроверочная → `active` рабочая →
`retired` выведена), лимит времени.

`generate(seed)` детерминирован: один seed — один и тот же вариант, поэтому вариант можно
восстановить и перепроверить. Наружу уходит только публичная часть (формулировка,
варианты ответа, код). Ключ ответа, id шаблона и seed остаются на сервере.

Форматы и примеры из банка (`bank_examples/`, по 2 шаблона на специализацию):

| Формат | Пример шаблона | Что меняется от варианта к варианту |
|---|---|---|
| `single_choice` — один ответ | Backend: сложность алгоритма; Frontend: специфичность CSS | код циклов, имена, селекторы, цвета, порядок вариантов |
| `multi_choice` — несколько ответов | QA: граничные значения; DS/ML: переобучение или недообучение | поле и диапазон, метод; метрики train/val, модель, набор утверждений |
| `numeric` — число | Backend: сколько строк вернёт JOIN; DS/ML: метрика по матрице ошибок | таблицы и тип JOIN; матрица и метрика |
| `short_text` — короткий ответ | QA: какой HTTP-код ожидать; DevOps: адрес сети / broadcast по CIDR | ситуация и ресурс; IP, маска, что спросить |
| `code_output` — что выведет код | Frontend: порядок вывода event loop JS | набор console.log / setTimeout / Promise / await, метки, задержки |
| `find_bug_line` — строка с ошибкой | Mobile: ошибка в Kotlin; DevOps: проблема в Dockerfile | вид ошибки, имена, лишние строки, стек (Python / Node / Go) |
| `ordering` — порядок шагов | Mobile: жизненный цикл Android Activity / Fragment | сценарий, имена активити, перемешивание |

Ответ генератор вычисляет сам, без запуска кода кандидата. Корректность генераторов
проверена тестами против настоящих систем: ответы SQL-шаблона сверяются с SQLite,
event loop — с выполнением кода в Node.js, CIDR — с модулем `ipaddress`, CSS — с
независимым подсчётом специфичности. Отдельный тест следит, чтобы позиция верного ответа
не повторялась: ни один ключ не встречается больше чем в половине вариантов.

Пример: два кандидата получают один шаблон «граничные значения» и видят разные задачи —
«Число гостей от 1 до 17», «Срок кредита от 4 до 114 мес.» — с разными числами
и в разном порядке. Ответ одного другому не подходит.

## 2. Модель IRT и оценка уровня

Используется двухпараметрическая логистическая модель (2PL):

P(верно | θ) = 1 / (1 + e^(−a·(θ − b)))

- θ — уровень кандидата (по популяции: среднее 0, разброс 1);
- b — сложность: при θ = b шанс ответить верно 50%;
- a — различающая сила: чем больше, тем резче задача отделяет тех, кто ниже b, от тех,
  кто выше.

Уровень оценивается методом EAP: на сетке θ от −4 до 4 (81 точка) считается
апостериорное распределение по всем ответам, оценка — его среднее, стандартная ошибка
(SE) — разброс. Априор — нормальный, центр зависит от заявленного грейда (Стажёр −1,5;
Junior −0,5; Middle 0,5; Senior 1,5). Это ускоряет старт, но уже после 6 ответов данные
перевешивают априор.

Варианты одного шаблона считаются равными по сложности: параметры генератора меняют
данные, а не суть задачи. Это допущение проверяется на реальных ответах: калибровка
по группам вариантов должна давать близкие `b` (см. «Ограничения»).

## 3. Адаптивный тест (CAT)

Каждый шаг:

1. Текущая θ — EAP по проверочным ответам с априором заявленного грейда. Первая задача
   поэтому подбирается под заявленный грейд.
2. Из банка убираются: уже показанные задачи; задачи, исключённые сервером (например,
   из прошлых попыток кандидата); задачи, которые показали больше чем в 25% сессий
   (контроль экспозиции); темы, которых в тесте уже 6 (баланс тем, не больше ~трети теста).
3. Для каждой задачи — информация Фишера a²·P·(1 − P) в текущей θ, поделённая на
   (1 + 0,1·k), где k — сколько задач этой темы уже было.
4. Выбирается **случайная задача из топ-5** (randomesque). Два кандидата с одинаковыми
   ответами всё равно получают разные наборы задач.

Остановка: SE < 0,35 (но не раньше 6 проверочных задач) или 15 проверочных задач.

**Непроверочные задачи.** В 1–2 случайные позиции среди первых шести показов вставляются
пилотные задачи. Кандидат их не отличает, на θ они не влияют, ответы идут в калибровку.
Так новые шаблоны (в том числе созданные по вакансиям) набирают статистику без риска для
оценки кандидата.

**Время.** Лимит на задачу (по умолчанию 180 с, у шаблона может быть свой). Время считает
сервер по своим часам и передаёт в движок; ответ после лимита засчитывается как неверный.
Время каждого ответа сохраняется — оно нужно детектору утечек.

**Состояние.** Сессия не хранит скрытого состояния: всё лежит в `SessionState` (JSON),
случайность выводится из seed сессии и номера шага. Сервер может сохранить сессию в БД
между запросами и восстановить её — результат будет тем же.

**Результат.** θ, SE, 90% доверительный интервал, число задач, разбор по темам: для каждой
темы сколько решено верно против ожидаемого при итоговой θ. Тема «сильная», если решено
заметно больше ожидаемого (на 0,2 задачи на задачу и больше), «слабая» — если меньше.
Правильные ответы кандидату не показываются, чтобы банк не утёк.

## 4. Грейд и правила смены

Пороги θ (настраиваются): Junior от −1,0; Middle от 0,0; Senior от 1,0; ниже −1,0 —
Стажёр. При нормальном распределении уровней это примерно 16% / 34% / 34% / 16%.

Решение по итогам теста на заявленный грейд:

| Исход | Условие | Что происходит |
|---|---|---|
| `passed_claimed` | θ не ниже порога заявленного грейда | грейд присваивается |
| `suggest_higher` | нижняя граница 90% ДИ (θ − 1,645·SE) выше порога следующего грейда | грейд присваивается, предлагается тест на грейд выше |
| `suggest_lower` | θ ниже порога заявленного грейда | грейд не присваивается (прежний, если был, сохраняется), предлагается тест на грейд ниже |

Принудительного понижения нет. Тест на Стажёра пройти можно всегда.

Частота (чистые функции от дат, возвращают причину и дату, когда станет можно):

- **смена грейда — не чаще раза в 90 дней** (интервал выбран по ТЗ: «раз в три месяца»);
- **повтор неудачной попытки на тот же грейд — через 30 дней;**
- первое присвоение грейда сменой не считается: после первого теста можно сразу пройти
  тест на грейд ниже (если не прошёл) или выше (если предложено), дальше действует 90 дней;
- подтверждение текущего грейда сменой не считается.

## 5. Детектор утечек

Работает по журналу ответов, по каждому шаблону, в скользящем окне последних 300 ответов.

1. **IRT-сигнал.** Ожидаемая доля верных = среднее P(верно) по θ отвечавших (θ считается
   без этой задачи, чтобы слитая задача сама не подтягивала оценку). z = (наблюдаемые −
   ожидаемые верные) / √Σ p(1 − p). Флаг: не меньше 30 ответов, z ≥ 3,5 и рост доли
   верных не меньше 10 п. п. Срабатывает при массовой утечке.
2. **Сигнал скорости.** «Быстрый верный» — верный ответ быстрее 35% медианного времени
   по задаче. Честно так отвечают редко, а слитый ответ просто вводят. Ожидаемая доля
   оценивается по всему банку устойчиво: берётся половина задач с наименьшей долей
   (не меньше 0,5%). Флаг: не меньше 4 быстрых верных и вероятность случайно получить
   столько (хвост Пуассона) меньше 10⁻⁴.

Помеченный шаблон выводится из оборота (`retired`), администратор получает уведомление.

**Аномалии кандидата:** два и больше быстрых верных ответа на задачи, которые для его
уровня сложные (шанс ниже 60% по θ без этой задачи); дополнительно индекс согласия
ответов l_z < −3. Это повод для ручной проверки, а не автоматическое наказание.

## 6. Калибровка

Пересчёт `a`, `b` шаблона по накопленным ответам при известных θ отвечавших:
логистическая регрессия ответа на θ, метод Ньютона со слабым априором вокруг текущих
значений (он не даёт параметрам «улететь» на малых выборках), рамки a ∈ [0,2; 4],
b ∈ [−4; 4]. Пилотная задача становится активной, когда: не меньше 150 ответов, оценка
сошлась, a ≥ 0,4, |b| ≤ 3,5, SE(b) ≤ 0,35.

## 7. Почему механика устойчива к распространению заданий

| Защита | Что делает | Чем подтверждено |
|---|---|---|
| Параметризация | у каждого кандидата свой вариант; слитый ответ подходит к чужому варианту лишь случайно | симуляция: выгода читеров почти исчезает (таблица «Утечка») |
| Большой банк | на одну специализацию нужно 120+ шаблонов, а не одна фиксированная анкета | таблица «Размер банка» |
| Адаптивность и случайный выбор из топ-5 | разные кандидаты видят разные наборы задач, «полного списка вопросов» не существует | у каждой сессии свой набор; доля показов задачи ограничена |
| Контроль экспозиции | ни одна задача не показывается больше чем в 25% сессий | симуляция: максимум 25,0% |
| Детектор утечек | слитая задача выводится из оборота автоматически | полнота 94%, точность 100% в симуляции |
| Непроверочные задачи | новые шаблоны проходят калибровку, не влияя на оценку; банк постоянно обновляется | тест «пилотные задачи не влияют на θ» |
| Ключ не покидает сервер | клиенту не уходят ответ, id шаблона и seed; после теста правильные ответы не показываются | тест публичной части варианта |

## 8. Почему не «одна нейросеть генерирует задания каждому»

ТЗ прямо называет проблему: уникальные задания от нейросети не гарантируют сопоставимую
сложность. У такой задачи нет измеренных `a` и `b`: два кандидата получают задания
неизвестной и разной трудности, и их результаты нельзя честно сравнить. Плюс нельзя
поручиться за правильность ключа.

У нас вариативность есть, но управляемая: генератор меняет данные внутри шаблона,
а сложность шаблона измерена на ответах и проверяется. Нейросеть используется там, где
она полезна и безопасна: по тексту вакансии она предлагает **черновики** новых шаблонов.
Черновик одобряет администратор, затем шаблон идёт в тесты как непроверочный, набирает
ответы, калибруется — и только после этого влияет на оценки.

## 9. Валидация (синтетическая)

Эталонной разметки в хакатоне нет, поэтому проверяем на синтетике, где истинный уровень
известен.

**Процедура.**
- Кандидаты: истинный θ ~ N(0, 1). Заявленный грейд: в 60% случаев истинный, по 20% —
  на грейд выше или ниже.
- Банк: 240 проверочных задач + 20 пилотных; a ~ логнормальное с медианой 1,3
  (0,6–2,5), b ~ равномерно от −2,8 до 2,8, 8 тем.
- Ответ: верен с вероятностью P(θ_истинный, a, b) по 2PL. Время: медиана задачи
  (40–150 с) × e^(0,15·(b − θ)) × логнормальный шум.
- Каждый кандидат проходит **настоящий** `CATSession` с правилами по умолчанию.
- Повтор: те же кандидаты проходят тест второй раз с другими seed.
- Утечка: сначала честный прогон, по нему сливаются 20% банка — с вероятностью,
  пропорциональной числу показов (утечь может только то, что видели). 10% кандидатов —
  «читеры»: на слитой задаче без параметризации отвечают верно и быстро; с
  параметризацией слитый ответ подходит, только если попался тот же вариант
  (вероятность 10% — консервативно, вариантов от 50). Детектор в режимах «+ детектор»
  запускается каждые 100 сессий и выводит помеченные задачи.

**Воспроизведение** (из корня репозитория, около минуты):

```
PYTHONPATH=backend python -m app.testing.engine.simulate --seed 20261011
```

Тесты с проверкой порогов (`PYTHONPATH=backend pytest backend/tests/engine`):
корреляция θ ≥ 0,85, длина ≤ 15, стабильность повтора, детектор находит слитые задачи.

- Точное попадание в грейд — 78%; почти все промахи — у кандидатов рядом с порогом:
  если истинный θ дальше 0,25 от порога, точность 88,5%.
- Стабильность: при повторе тот же грейд у 68% (каппа 0,56 — умеренное согласие), то же
  решение по заявленному грейду («подтверждён / нет») — у 86%. Это предел теста из 6–15
  задач при четырёх полосах шириной в одну единицу θ. Длиннее тест — стабильнее
  (таблица «Длина теста»); это настройка `CATConfig`, а не переделка.
- Ошибка калибровки ±0,2 почти не портит результат (корреляция 0,932).
- r_pb в адаптивном тесте ниже, чем в обычном (0,27 против 0,35), — так и должно быть:
  адаптивный тест подбирает задачи под уровень, разброс отвечающих по каждой задаче мал.
- Утечка без защиты резко завышает грейд читерам (85% против 10% фона). Параметризация
  возвращает картину почти к фону (14%). Если задача всё же одна на всех, детектор
  находит 94% слитых без ложных срабатываний и снижает завышение до 38% — часть читеров
  успевает пройти тест до проверки.
- Почти всю работу детектора делает сигнал скорости (72,9% против 6,2% у IRT-сигнала):
  при 10% читеров IRT-сигнал слаб, потому что θ читера сама завышена слитыми задачами.
  Детектор кандидатов в режиме без защиты находит 83% читеров без ложных обвинений.
- С параметризацией детектору почти нечего ловить: слитый ответ редко подходит, сигнала
  нет — и вреда тоже нет. Это ожидаемо: два уровня защиты страхуют друг друга.
- Размер банка: 120–240 задач дают SE 0,34–0,37 за 12–15 задач. При 15 задачах тест
  показывает весь банк, при 30 — половину, и до SE 0,35 не доходит. Провал на 60 задачах —
  эффект контроля экспозиции: хороших задач мало, лимит 25% заставляет брать слабые
  (проверено отдельно: без лимита на тех же 60 задачах SE 0,37 и корреляция 0,935).
  Вывод: жёсткий лимит экспозиции оправдан при большом банке; для небольшого его стоит
  поднять.
- Калибровка по 300 ответам восстанавливает `b` с ошибкой ≈ 0,23 и `a` ≈ 0,20 при
  неточной θ отвечавших (SE 0,3); 90% пилотных задач проходят правило перевода в рабочие.

## 10. Ограничения и что дальше

- **Банк MVP мал для адаптивности.** План — 15 шаблонов на специализацию; при лимите 15
  задач тест тогда показывает весь банк и адаптивность пропадает (таблица «Размер банка»:
  при 15 задачах SE ≈ 0,48, корреляция 0,90). Для рабочего режима нужно 120+ шаблонов на
  специализацию; до этого результат — оценка по фиксированному набору с IRT-взвешиванием,
  а лимит экспозиции для маленького банка стоит поднять (`CATConfig.max_exposure_rate`).
- **Модель времени — допущение.** Сигнал скорости силён в симуляции, потому что честные
  ответы в ней редко бывают очень быстрыми. На реальных данных долю быстрых ответов
  нужно оценивать по истории (код уже делает это по всему банку) и проверять пороги.
- **Равенство вариантов внутри шаблона** надо проверять на реальных ответах: разбить
  ответы по группам вариантов и сравнить `b`. Шаблоны с большим разбросом — дробить.
- **Пороги грейдов** (−1 / 0 / 1) — стартовые. После набора данных их стоит
  согласовать с экспертной оценкой (стандартная процедура установления порогов).
- **Детектор срабатывает с задержкой** (раз в N сессий); в проде — по расписанию и после
  каждой волны тестов.
