## Что просило ТЗ и что сделали мы

Ниже идём по ТЗ: что требовалось и что есть у нас. Всё перечисленное работает на стенде, на
настоящей базе. Цифры взяты из отчёта валидации ([раздел 4](04_validation.md)), тот же отчёт
показывает экран «Валидация» в админке.

### Обратная механика подбора — главный критерий (35%)

**ТЗ:** работодатель сам находит категорию и выходит на конкретного кандидата с предложением и
зарплатой (по образцу LHH). Ранжирование внутри категории, объяснимость выдачи, фильтры без потери
подборки. Проверка — доля релевантных кандидатов в топе.

**Что сделали:**

- Работодатель описывает потребность обычной фразой («мидл питонист на бэк, джанго/постгрес,
  гибрид, 180-250к») — кнопка «Разобрать» раскладывает её по полям: специализация, грейд, стек,
  формат, вилка. На 12 тестовых фразах — 12 из 12 верно.
- Система предлагает категории: основную, соседний грейд и смежные направления, с числом
  кандидатов в каждой.
- Внутри категории — счёт 0–100 из шести факторов: стек 0,30, тест 0,25, ФСП 0,15, свежесть
  профиля 0,10, зарплата 0,10, формат 0,10. Веса админ меняет без релиза.
- У каждого кандидата в подборке — «Почему в подборке» (2–4 причины) и полоски вклада каждого
  фактора. Работодатель видит, за что человек поднят выше.
- Фильтры сужают подборку, но не пересчитывают её: «Показано N из M · исходная подборка
  сохранена», одна кнопка возвращает исходную.
- Банк кандидатов — вся база с фильтрами по специализации, грейду, категории, стеку и наличию
  достижений ФСП, отсортированная под выбранную потребность с процентом соответствия.
- Приглашение без обязательной вакансии: описание, вилка от–до, способ связи, вопрос к созвону.
  Вилку ниже ожиданий кандидата отправить нельзя (сами ожидания работодателю не показываются).
  Подсказка «обычно принимают от …» и вероятность принятия. Квота 20 активных приглашений, срок
  ответа 7 дней, отказ — с причиной.
- До принятия приглашения профиль обезличен («Кандидат #XXXX»). ФИО и контакты открываются
  только после «Принять».

**Результат** (100 потребностей, 1200 синтетических кандидатов с известным ответом):

| Метрика | Наш подбор | Поиск по ключевым словам (BM25) |
|---|---|---|
| precision@10 | **0,486** | 0,253 |
| nDCG@10 | **0,577** | 0,313 |
| recall@50 | **0,778** | 0,577 |

В топ-10 у нас в среднем 4,9 подходящих кандидата против 2,5 — **почти вдвое больше**. Наш подбор
лучше поиска по словам в 87 потребностях из 100. Жюри может загрузить свои пары «вакансия –
кандидат» на экране «Валидация» и сразу получить те же метрики.

### Тест, устойчивый к утечкам, и категоризация (25%)

**ТЗ:** один набор заданий на всех разойдётся по рынку, генерация нейросетью не даёт сравнимой
сложности. Нужен подход, устойчивый к обеим проблемам. Грейд не понижать принудительно, смену
грейда ограничить по времени. Показать, как из описаний вакансий собираются тесты.

**Что сделали:**

- Задача в банке — не текст, а **параметрический шаблон**: числа, код и порядок ответов
  генерируются под каждого кандидата. 192 рабочих шаблона, по 32 на каждое из 6 направлений;
  у 190 из них больше 100 различных вариантов. Слитый ответ к чужому варианту не подходит.
- Сложность каждого шаблона **измерена** (модель IRT 2PL) и пересчитывается по реальным ответам.
  Поэтому у разных кандидатов разные задачи, но сравнимая сложность — ровно то, чего нет
  у чистой генерации нейросетью.
- Тест **адаптивный**: следующая задача подбирается под текущую оценку уровня, до 20 задач.
- **Детектор утечек** находит задачи, которые стали решать «слишком верно и слишком быстро»,
  и выводит их из оборота. Правильные ответы кандидату не показываем.
- Ключи ответов проверены исполнением: SQL — в SQLite и PostgreSQL, JS — в Node.js, Python —
  интерпретатором.
- Путь кандидата по ТЗ: опрос из 8 вопросов → рекомендация направления → выбор грейда → тест →
  категория. Грейд из PDF-резюме — только заявка с пометкой «заявлено, подтвердите тестом».
- Грейд принудительно не понижается. Не сдал заявленный — можно сразу взять категорию по
  уровню, который тест намерил, или пройти тест на грейд ниже. Смена грейда — не чаще раза
  в 90 дней, повтор неудачной попытки — через 30. При пересдаче сначала идут шаблоны, которых
  у кандидата ещё не было.
- Тест из текста вакансии: админ вставляет вакансию — система находит темы и собирает тест
  из банка. На 5 вакансиях: специализация 5/5, грейд 5/5, темы 25/25. Если темы в банке нет,
  нейросеть пишет черновик шаблона, но в тест он попадает **только после одобрения человеком**.

**Результат:**

| Что проверяли | Результат |
|---|---|
| Оценка теста против истинного уровня | корреляция **0,94** |
| Категория совпала с истинной точно / в пределах грейда | **78,8% / 100%** (по заявленному грейду было бы 64,9%) |
| Завысил грейд при регистрации → тест вернул истинный | 74,4% |
| Повторное прохождение дало ту же категорию | 75,6%, каппа Коэна 0,66 |
| Различающая сила задач | 0,43 в среднем, у 100% шаблонов выше 0,2 |
| Слили 20% банка: доля завышенных грейдов у списывающих | **39% → 12,7%** с параметризацией (фон у честных 10,7%) |
| Детектор утечек: найдено слитых / ложных срабатываний | все 36 из 36 / 2 из 156 |

### Интерфейс (10%)

- Цвета и шрифт по брендбуку ФСП.
- Кандидат видит свой профиль глазами работодателя («Так вас видит работодатель»).
- Профиль попадает в поиск только после явного согласия на публикацию.
- У каждого экрана есть состояния загрузки, пустого списка и ошибки; подсказки — простым языком.
- Адаптивная вёрстка до 390 px: таблицы превращаются в карточки.

### Техническая проработка (7%)

- Frontend (React + TypeScript), Backend (FastAPI, Python 3.12), PostgreSQL 16 — как просит ТЗ 3.5.
  Бэкенд — модульный монолит со слабо связанными модулями, не хранит состояние и
  масштабируется добавлением копий.
- Весь стек поднимается одной командой `docker compose up`. HTTPS через Caddy.
- Все методы API описаны в OpenAPI (Swagger на стенде), ошибки в едином формате
  `{code, message, details}`.
- 152-ФЗ: отдельные согласия на обработку и на публикацию, права по ролям, пароли в виде хеша,
  API-токены хранятся хешем и показываются один раз.
- Открытый код под MIT, зависимости под MIT / BSD / Apache.

### Полнота и кандидат без ФСП (6%)

- Весь обязательный путь соискателя работает: регистрация по почте с подтверждением → профиль
  (вручную или из PDF с автораспознаванием) → опрос → тест → категория → приглашение.
- Стандартизированный PDF-профиль генерируется автоматически.
- **ФСП ID на Keycloak** (OpenID Connect + PKCE) — как раз то, на чём ФСП собирается строить свой ID.
  Достижения приходят из реестра (наш мок с описанным контрактом API), превращаются в бейджи
  и входят в ранжирование.
- Кандидат без истории ФСП проходит весь путь и **не штрафуется**: фактор ФСП = 0, работодатель
  видит «Нет подтверждённых достижений ФСП. Это не минус — оценивайте по тесту».
- Документация закрывает все 8 пунктов ТЗ 3.4 (оглавление ниже).

### Нейросеть: на стенде и в закрытом контуре ФСП

**Где помогает.** Нейросеть дополняет правила в трёх местах:

- **черновики заданий из вакансии** — для темы, которой нет в банке; в тест черновик попадает
  только после одобрения человеком;
- **разбор потребности работодателя** из живого текста («нужен чел на айос, свифт, года три
  опыта, до 280к, удалёнка» → Mobile · Middle, Swift, удалёнка, до 280 000);
- **разбор PDF-резюме** — дочитывает поля, которые правила не нашли.

Категорию кандидата и место в выдаче нейросеть **не решает** — только тест и формула
ранжирования. Если нейросеть не ответила, всё работает на правилах, пользователь ошибки не видит.
На экране честно помечено, кто написал черновик: нейросеть или словарь тем.

**На стенде** для показа жюри подключена GPT-4.1 mini через OpenAI-совместимый API.

**Для закрытого контура ФСП основа уже готова.** В репозитории лежит локальная открытая
модель: Qwen2.5-1.5B-Instruct (лицензия Apache 2.0) в llama.cpp (MIT), отдельным контейнером
`llm` в `infra/stand/compose.yml`. Она работает на том же сервере, порт наружу не открыт,
тексты резюме и потребностей никуда не уходят — это закрывает вопрос 152-ФЗ. Ответы модели
идут строго по JSON-схеме: llama.cpp не даёт ей ответить в другом формате. Помещается в
сервер на 2 ядра и 4 ГБ вместе со всем стеком.

Переключение на локальную модель — три действия:

1. Положить файл модели `qwen2.5-1.5b-instruct-q4_k_m.gguf` (≈ 1,1 ГБ, Hugging Face
   `Qwen/Qwen2.5-1.5B-Instruct-GGUF`) в `/opt/fsp-talent/models`. Без интернета — скачать на
   любой машине и перенести файлом. На нашем сервере файл уже лежит.
2. В `infra/stand/.env` добавить `COMPOSE_PROFILES=llm` и убрать строки, которые начинаются
   с `LLM_`, — по умолчанию бэкенд сам смотрит в локальную модель.
3. `docker compose -f infra/stand/compose.yml --env-file infra/stand/.env up -d`.

Код при этом не меняется. Так же одной настройкой подключается любая другая модель: свой GGUF-файл
или внешний OpenAI-совместимый сервис. Подробно — [раздел 9](09_llm.md).

## Решение в пяти пунктах

1. **Обратная механика подбора.** Работодатель описывает потребность, получает подборку
   по категориям (специализация × грейд) с объяснением «почему в подборке» и сам приглашает
   кандидата с обязательной зарплатной вилкой. Контакты открываются только после принятия
   приглашения. Квота приглашений, запрет вилки ниже ожиданий кандидата, отказ с причиной,
   рыночная подсказка «обычно принимают от X ₽».
2. **Категорию определяет тест, а не резюме.** Опрос → выбор грейда → адаптивный тест (IRT, CAT)
   на банке из 192 параметрических шаблонов. Грейд принудительно не понижается, смена — не чаще
   раза в 90 дней.
3. **Тест устойчив к утечкам.** У каждого кандидата свой вариант задачи, сложность шаблонов
   измерена и калибруется по ответам, детектор утечек автоматически выводит «слитые» задачи.
   Нейросеть только предлагает черновики заданий по тексту вакансии — оценку она не делает.
4. **Подтверждённый профиль.** Достижения ФСП приходят из реестра через привязку ФСП ID
   (Keycloak, OIDC), превращаются в бейджи и ФСП-скор и входят в ранжирование. Кандидат без
   истории ФСП не штрафуется.
5. **Проверено на данных с известным ответом.** На 1200 синтетических кандидатах тест
   восстанавливает уровень с корреляцией 0,94 и ставит верную категорию в 78,8% случаев
   (ошибка больше чем на грейд — 0%; заявленный грейд верен лишь в 64,9%). Подбор даёт
   precision@10 0,486 против 0,253 у поиска по ключевым словам резюме. Параметризация снижает
   выгоду от утечки 20% банка с 39% до 12,7% завышенных грейдов. Жюри может загрузить свои
   пары и получить метрики.

## Документ одним файлом (DOCX и PDF)

Готовые файлы: [`fsp-talent-documentation.pdf`](fsp-talent-documentation.pdf) и
[`fsp-talent-documentation.docx`](fsp-talent-documentation.docx) — все разделы в порядке
оглавления, с титульным листом, оглавлением, диаграммами и графиками валидации.

Разделы написаны в Markdown с диаграммами mermaid. Сборка (нужны Node.js для mermaid-cli
и Docker для pandoc и LibreOffice):

```bash
python docs/solution/tools/gen_api_table.py      # таблица раздела 6 из openapi.json
python docs/solution/tools/gen_libraries.py      # раздел 7 (при поднятом docker compose)
python docs/solution/tools/build_docs.py         # → docs/solution/fsp-talent-documentation.{docx,pdf}
```

`build_docs.py` склеивает разделы (`build_bundle.py --render-mermaid`: диаграммы → PNG,
ссылки между разделами → якоря, остальные ссылки → GitHub), конвертирует в DOCX через pandoc
и обновляет оглавление и экспортирует PDF в LibreOffice.
