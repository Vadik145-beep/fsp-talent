# 4. Процедура валидации и результаты

Готовых датасетов и эталонной разметки в хакатоне нет [ТЗ 2], поэтому мы проверяем решение
на **собственных синтетических данных, где правильный ответ известен заранее**, и на небольших
наборах реальных по форме текстов (резюме, вакансии, формулировки потребностей) с ручной
разметкой. Полный отчёт с графиками — [`docs/validation/report.md`](../validation/report.md).

## 4.1. Принципы

1. **Скрытая истина.** У синтетического кандидата есть истинный уровень θ, который система
   не видит; она видит только его ответы, сгенерированные по модели IRT. Поэтому точность
   грейда можно посчитать честно.
2. **Разметка не повторяет формулу.** Эталон релевантности пар «потребность — кандидат»
   строится по отдельному правилу, а не по формуле ранжирования, — иначе метрика подбора
   проверяла бы сама себя.
3. **Настоящий код.** Симуляции прогоняют те же функции, что работают в продукте
   (`CATSession`, `decide`, `detect_leaks`, `calibrate_item`, `score_candidate`), а не их копии.
4. **Воспроизводимость.** Фиксированный seed, одна команда — те же цифры. Пороги ключевых
   метрик зашиты в автотесты: если код испортит качество, CI упадёт.
5. **Жюри может проверить само** — загрузить свои пары и получить метрики (4.6).

## 4.2. Что проверяем и чем — по критериям ТЗ 6.1 и 6.2

## 4.4. Результаты: механика тестирования

Проверок две, и цифры в них разные, потому что разные условия:

- **Платформа на текущем банке** (4.4.1) — настоящий онбординг (тест на заявленный грейд,
  при неудаче — ниже, при уверенном прохождении — выше) на рабочем банке 192 шаблона
  (32 на направление) с настройками стенда: стоп при SE < 0,30, максимум 20 задач. Это то,
  что получит кандидат сегодня.
- **Движок на большом синтетическом банке** (4.4.2) — 240 задач на одно направление,
  стоп при SE < 0,35 или 15 задачах. Показывает, как механика работает, когда банк вырастет.

Банк в админке («Банк задач») показывает 222 записи: 192 рабочих шаблона движка
и 30 демо-записей из фикстур `data/seed/items.json` (метрики и предпросмотр для показа
экранов). У демо-записей нет генератора в движке, в адаптивный тест и в валидацию они
не попадают.

### 4.4.2. Движок на большом синтетическом банке

Синтетическая валидация движка, seed 20261011 (подробно — [`docs/testing/engine.md`](../testing/engine.md) §9):

| Метрика | Значение |
|---|---|
| Корреляция θ̂ с истинным θ / RMSE | 0,945 / 0,332 |
| Грейд точно / ±1 | 78,4% / 100% |
| Грейд точно, если θ дальше 0,25 от порога | 88,5% |
| Средняя длина теста | 12,8 задачи (максимум 15) |
| Повтор: тот же грейд / каппа Коэна / корреляция θ̂₁ и θ̂₂ | 67,9% / 0,558 / 0,891 |
| Повтор: то же решение по заявленному грейду / каппа | 86,4% / 0,587 |
| Правило продукта (SE < 0,30 или 20 задач): грейд точно; повтор — тот же грейд / каппа | 80,1%; 73,6% / 0,636 |
| Средняя `a`; r_pb на линейной форме (доля > 0,2) | 1,32; 0,348 (100%) |
| Утечка без защиты: грейд завышен у читеров / у честных | 85,0% / 9,9% |
| Утечка + параметризация: грейд завышен у читеров / у честных | 14,0% / 9,8% |
| Детектор задач (одна задача на всех): точность / полнота | 100% / 93,8% |
| Калибровка (30 пилотов × 300 ответов): RMSE `a` / `b` | 0,198 / 0,228 |

Как читать: ошибка грейда больше чем на один уровень — 0%; почти все промахи — у кандидатов
рядом с порогом. Стабильность «тот же грейд при повторе» ограничена длиной теста при четырёх
полосах шириной в одну единицу θ; более длинный тест стабильнее — это настройка, а не переделка.
Условия утечки здесь другие (другой банк, правило остановки, частота запуска детектора),
поэтому проценты завышения у читеров (85% без защиты) напрямую с 4.4.1 (39%) не сравниваются;
вывод одинаков: параметризация возвращает картину к фону честных кандидатов.

## 4.5. Результаты: подбор

100 потребностей, 1200 кандидатов. Эталон «подходит» строится только по скрытой правде:
истинное направление совпадает, кандидат *реально* владеет всеми обязательными технологиями
(истинный стек, а не резюме), минимальная зарплата не выше «до» вилки; оценка 2 — истинный
грейд равен грейду потребности, 1 — на ступень выше (переквалифицирован), иначе 0. Эталон
специально не повторяет формулу: он не видит ФСП, свежесть, формат и желательный стек,
а платформа не видит истинный уровень и стек ([`report.md`](../validation/report.md), раздел 3).

Платформа строит выдачу так, как её видит рекрутер: сначала основная категория потребности
(категория — из теста), затем рекомендованные соседние категории, затем остальные; внутри —
по счёту `score_candidate` с весами по умолчанию. В скобках — 95% бутстреп-интервал по
потребностям.

| Метрика | Платформа | Ключевые слова резюме (BM25) | Только категория | Случайно |
|---|---|---|---|---|
| **precision@10** | **0,486** (0,44–0,53) | 0,253 (0,23–0,28) | 0,216 | 0,013 |
| мягкая precision@10 (оценка ≥ 1) | 0,560 | 0,294 | 0,237 | 0,016 |
| **nDCG@10** | **0,577** (0,54–0,62) | 0,313 (0,28–0,34) | 0,236 | 0,014 |
| recall@50 | 0,778 (0,75–0,81) | 0,577 (0,54–0,62) | 0,649 | 0,044 |
| Доля всех подходящих, попавших в топ-10 | 29,9% | 15,6% | — | — |

«Только категория» — кандидаты категории из теста сверху, внутри случайный порядок: показывает,
сколько даёт сама категоризация без формулы счёта.

Платформа ставит в топ-10 в среднем 4,9 подходящих из 10, поиск по ключевым словам — 2,5,
случайный выбор — 0,13; интервалы не пересекаются. По nDCG@10 платформа лучше ключевых слов
в 87 потребностях из 100. Если все кандидаты пройдут тест заново, топ-10 совпадает в среднем
на 62% (меняются кандидаты на границе категорий); при одних и тех же данных выдача
детерминирована.

![precision@10 и nDCG@10 по способам](../validation/img/precision_at_10.png)

**Вклад компонентов (абляция).**

| Вариант | precision@10 | nDCG@10 | recall@50 |
|---|---|---|---|
| Вся формула (веса по умолчанию) | 0,486 | 0,577 | 0,778 |
| Без теста: категория по заявленному грейду, θ нет | 0,435 | 0,543 | 0,782 |
| Без категорий: только счёт по всей базе | 0,213 | 0,266 | 0,527 |
| Без стека (вес 0) | 0,263 | 0,293 | 0,708 |
| Без синонимов и смежности технологий | 0,393 | 0,473 | 0,732 |
| Без ФСП (вес 0) | 0,485 | 0,583 | 0,776 |
| Без θ в счёте (вес 0; категория из теста остаётся) | 0,511 | 0,620 | 0,775 |

![Абляция формулы подбора](../validation/img/matching_ablation.png)

- **Главный вклад — тест и категории.** Без категорий precision@10 падает до 0,213;
  с категорией по заявленному грейду вместо теста — до 0,435: тест исправляет завышенные грейды.
- **Стек и справочник синонимов** — второй по силе: без стека 0,263, без синонимов 0,393
  («постгрес» и «k8s» в резюме иначе теряются). Здесь и проигрывает поиск по ключевым словам.
- **ФСП** метрики почти не меняет (0,485): наш эталон его не учитывает. ФСП в счёте — требование
  ТЗ и сигнал для рекрутера; важно, что он не ухудшает выдачу.
- **θ внутри категории слегка снижает соответствие эталону:** 0,486 с θ против 0,511 без θ.
  Внутри категории θ поднимает самых сильных, а среди них чаще переквалифицированные — их
  истинный грейд на ступень выше, и эталон считает их подходящими лишь частично. Это
  расхождение между ТЗ («выше — сильнее подтверждённый профиль») и строгой разметкой «точно
  этот грейд».

| Вес θ (остальные — пропорционально) | precision@10 | nDCG@10 |
|---|---|---|
| 0,00 | 0,511 | 0,620 |
| 0,10 | 0,502 | 0,608 |
| 0,25 (по умолчанию) | 0,486 | 0,577 |
| 0,40 | 0,449 | 0,532 |

**Рекомендация:** θ оставить в счёте (этого требует ТЗ), но снизить вес с 0,25 до 0,10 —
precision@10 0,502 вместо 0,486. Веса — настройка платформы (`ranking_weights`), админ меняет
их на экране «Справочники» без релиза; в демо-данных оставлены веса по умолчанию, на которых
посчитаны все цифры этого раздела.

## 4.7. Как воспроизвести и проверить самим

| Что | Команда (из корня репозитория) |
|---|---|
| Симуляция движка теста (около минуты) | `PYTHONPATH=backend python -m app.testing.engine.simulate --seed 20261011` |
| Пороги движка в автотестах | `PYTHONPATH=backend pytest backend/tests/engine` |
| Отчёты по разбору текстов | `cd backend && python -m app.nlp.validation` |
| Полная валидация платформы: данные, симуляции, графики, `report.md` (~3–4 минуты, БД не нужна) | `pip install -e "backend[dev]" matplotlib`, затем `make validate` (= `python scripts/validation/run_all.py`) |
| Метрики и API проверки в автотестах | `pytest backend/tests/test_eval_metrics.py backend/tests/test_eval_api.py` |

В интерфейсе: кабинет администратора → «Валидация» (`/admin/validation`) — графики точности
грейда, стабильности повтора, различающей силы, precision@10, работы детектора утечек
(`GET /api/eval/validation`).

**Проверка подбора на своих данных:** `POST /api/eval/matching` (или экран «Валидация») —
загрузить CSV с колонками `need_id`, `candidate_id` и необязательно `relevant` (0/1 или 0/1/2
с «частично»). Порядок строк не важен: кандидатов каждой потребности ранжирует сама платформа,
а метрики показывают, сколько подходящих оказалось наверху. Id — синтетические (`N001`…,
`C0001`…) или реальные id потребностей и профилей стенда. Пример —
`data/validation/example_pairs.csv` (6 потребностей × 40 кандидатов): precision@10 0,733,
nDCG@10 0,786 против 0,617 / 0,679 у поиска по словам и 0,250 при случайном порядке.

curl -F file=@data/validation/example_pairs.csv https://159-194-200-243.sslip.io/api/eval/matching

## 4.8. Ограничения валидации

- Синтетика проверяет, что механика делает то, что задумано, при известных допущениях
  (модель ответов 2PL, модель времени). На реальных людях пороги детектора и грейдов
  нужно уточнить по накопленным данным — механизмы для этого (калибровка, настраиваемые
  пороги) уже в продукте.
- Синтетика — не рынок: распределения уровней, стека, зарплат и поведения (завышение грейда,
  приписки в резюме) — наши допущения. Процедура переносится на реальные данные без изменений:
  нужна экспертная разметка пар, её можно загрузить через `POST /api/eval/matching`.
- Эталон подбора написан нами; правило специально не совпадает с формулой, но выбор признаков
  эталона (например, ФСП не считается признаком соответствия) — тоже наше решение.
- Банк из 32 шаблонов на направление ограничивает точность и стабильность теста (4.4.1).
- Образцы для разбора текстов маленькие (5–12 штук); это проверка работоспособности, а не
  статистическая оценка точности.
